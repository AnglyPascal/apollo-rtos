\section{The Apollo Guidance Computer}
\label{sec:agc}

The \textbf{Apollo Guidance Computer} (AGC) was an early digital computer developed in
the 1960s to provide real-time navigation and control for the Apollo spacecraft.
Despite operating under severe hardware constraints, it became a cornerstone of the
Apollo program’s success.

The AGC featured a \textit{2.048 MHz} CPU capable of executing approximately
\textit{40,000 instructions per second}. It used a \textit{16-bit word length}, with 15
bits for data and 1 parity bit. The memory system combined \textit{2 kilowords} (4KB)
of erasable magnetic-core non-volatile RAM with \textit{36 kilowords} (72KB) of fixed
core rope ROM to store both software and mission data.

Astronauts interacted with the AGC through the \textit{Display and Keyboard} (DSKY)
unit—a 21-digit segmented display coupled with a 19-button keypad—enabling manual
command input and real-time monitoring. This human-machine interface was critical for
spacecraft operation, particularly during complex maneuvers.

Given the severe resource limitations, the AGC operating system, known as \emph{the
Executive}, was engineered for maximum efficiency. It prioritized critical tasks,
ensured graceful degradation under faults, and maintained system stability even after
resets or failures.

The following subsections summarize the main architectural features of the AGC
Executive, based primarily on \citet{agc_book}.


\subsection{The Executive}

The \textbf{Executive} was the core component responsible for allocating system
resources such as CPU time and dynamic memory to processes. It implemented a
\emph{priority-based cooperative scheduling} algorithm, summarized as follows:

\begin{emptythm}
    \begin{itemize}[left=8pt]
        \item The highest-priority process has exclusive access to the CPU.
        \item Lower-priority processes remain idle until the highest-priority process:
            \begin{itemize}
                \item lowers its priority, or
                \item enters \texttt{sleep} while waiting for an event.
            \end{itemize}
        \item If a new process with higher priority is scheduled while another is
            running:
            \begin{itemize}
                \item the new process waits until the current process lowers its
                    priority or sleeps,
                \item then immediately starts execution.
            \end{itemize}
    \end{itemize}
\end{emptythm}

\paragraph*{Core Sets} Process metadata was maintained in a table called \textbf{Core
Sets}, similar to modern process descriptors. Each active process occupied one Core
Set. The system supported:
\begin{itemize}
    \item 6 Core Sets in the Command Module, and
    \item 7 Core Sets in the Lunar Module.
\end{itemize}

\paragraph*{Addressable Memory} Each process was allocated 7 words of private memory,
typically used for general computation. In interpreter mode, these acted as accumulator
registers. Processes requiring more memory could request 42 additional words from the
Vector Accumulator (VAC) area.

\paragraph*{Starting a New Process} When a process was created, it did not immediately
preempt the CPU, even if it had higher priority. A special register, \texttt{NEWJOB},
indicated the ID of the highest-priority runnable process:
\begin{itemize}
    \item \texttt{NEWJOB == 0} indicated the current process was the highest-priority.
    \item A nonzero value \texttt{d} indicated that the process represented by Core Set
        \texttt{d} had higher priority.
\end{itemize}
Upon new process creation, \texttt{NEWJOB} was updated if the new process had higher
priority than the currently running one.

\paragraph*{Process Switching} Context switches occurred only when the current process
voluntarily yielded control. A running process was required to check \texttt{NEWJOB} at
least every 20 ms to detect higher-priority contenders. Failure to check
\texttt{NEWJOB} for more than 640 ms was treated as a stall, triggering a hardware
restart.

During a switch, the current process's context was saved in Core Set 0, and the context
of the new process, identified by \texttt{NEWJOB}, was restored by swapping with the
context of the current process. Execution then resumed automatically from the last
instruction of the switched-in process.

If a process relinquished execution—either by sleeping or lowering its priority—the
system scanned the Core Set table to find and schedule the next highest-priority
runnable process.

\paragraph*{Sleep and Wakeup} A process could enter \texttt{sleep} to wait for an
external event. The \texttt{JOBSLEEP} instruction marked the process as sleeping by
negating its priority, allowing the next eligible process to run.

When the awaited event occurred, another process could wake it using \texttt{JOBWAKE},
which reversed the priority negation. \texttt{JOBWAKE} also checked \texttt{NEWJOB} to
determine whether the woken process has highest priority.

Processes could also delay themselves for a fixed duration using \texttt{DELAYJOB},
which scheduled an ``alarm" via the \emph{waitlist} mechanism.

\paragraph*{The Waitlist} The \textbf{waitlist} introduced preemptive capabilities to
the otherwise cooperative Executive, allowing tasks to be scheduled with precise
deadlines. Conceptually, it was a \emph{sorted linked list} of tasks ordered by
deadline. When a new task \(t\) was added, it was inserted such that:
\begin{itemize}
    \item any task \(t_0\) with an earlier deadline appeared before \(t\), and
    \item any task \(t_1\) with a later deadline appeared after \(t\).
\end{itemize}

Every 10 ms, a timer interrupt checked if the earliest task had reached its deadline.
If so, the task was executed and removed from the list. Waitlist tasks, executed inside
the interrupt handler, were required to be brief—typically under 5 ms or 150–200
instructions.

\subsection{Restart Mechanism}

Despite its limited resources, the AGC was engineered to achieve high reliability, even
in the presence of faults. Modern CPU and OS designs dedicate extensive resources to
error detection and recovery; by contrast, the AGC lacked hardware support for
sophisticated fault management. In particular, the absence of a memory protection unit
made reliable detection of memory corruption nearly impossible.

Instead, the AGC adopted a radical but effective strategy: \vspace{-1em}
\begin{center}
    \emph{Just restart everything.}
\end{center}
\vspace{-1em} Restarting the system at arbitrary points posed some challenges, as
critical tasks could be interrupted mid-execution. To address this, the AGC organized
programs into six \emph{restart groups}, each capable of recovering one process at a
time. Within each group, programs could define specific restart phases, corresponding
to unique recovery routines. As a program progressed, it could update its active
restart phase via the \texttt{PHASCHNG} routine.

Each restart group could be configured to use one of four restart behaviors, determined
by the restart phase number:
\begin{itemize}
    \item \textbf{Inhibit group restart (G.0):} Suppresses any recovery; no process in
        the group is restarted.
    \item \textbf{Restart last display (G.1):} Restores the most recent DSKY display
        output, without executing program logic.
    \item \textbf{Execute one restart routine (G.Odd > 1):} Invokes a single recovery
        procedure for the group’s program.
    \item \textbf{Execute two restart routines (G.Even):} Invokes two
        routines—typically one for cleanup and one for resuming execution.
\end{itemize}

To minimize overhead, recovery information was stored in a compressed format within the
\emph{phase tables}. During a restart:
\begin{itemize}
    \item All active jobs and waitlist tasks were canceled.
    \item Interrupts were disabled, and system tables were cleared and reinitialized.
    \item The integrity of the restart phase table was verified, and recovery routines
        for each group were executed sequentially.
\end{itemize}

These mechanisms enabled the AGC to gracefully recover from a wide range of faults—an
essential requirement for spacecraft systems where failure tolerance was critical to
mission success. This was made possible in part by the use of magnetic core memory,
which retained its contents even after power loss, allowing the system to resume
operation without reinitializing its entire state.


\subsubsection{The 1201 and 1202 Alarms During Apollo 11's Lunar Descent}

The Apollo 11 lunar landing provided a dramatic demonstration of the AGC's resilience.
During the final descent to the Moon, the Lunar Module's guidance computer triggered
unexpected alarms—specifically, program alarms 1201 and 1202. These alarms indicated
\emph{executive overflows}, meaning the system's scheduler was overloaded and unable to
complete all tasks within real-time constraints.

The root cause was traced to the rendezvous radar being left active during descent,
introducing spurious data due to a hardware quirk \citep*{witt_2019_apollo}. This
unexpected input consumed significant CPU time, reducing the availability of
computational resources for other tasks. An additional command to display altitude data
further strained the system, ultimately triggering the alarms.

Despite these conditions, the AGC's design allowed it to prioritize critical tasks. On
detecting overload, the system gracefully shed nonessential processes through a
controlled restart while maintaining key operations such as engine control and
navigation. Mission Control evaluated the situation and, trusting the system's
robustness, authorized the crew to proceed. Thanks to this resilience, Apollo 11
successfully landed on the Moon, transforming a potential abort into a historic
achievement.

\subsection{Interpreter}

To extend its limited native instruction set, the AGC incorporated a custom virtual
machine known as the \textbf{Interpreter}. The Interpreter operated as a
\textit{bytecode engine} layered atop the AGC's basic instruction set, enabling the
execution of more complex \textit{pseudo-instructions} while conserving memory and
improving computational efficiency for critical tasks.

The Interpreter provided a broader set of operations, including arithmetic,
trigonometric, vector and matrix calculations, data manipulation, and sophisticated
branching. These extensions were essential for supporting the advanced navigation and
guidance computations required during spaceflight.

While the AGC's native instruction set emphasized speed, the Interpreter introduced
compact, high-level mathematical functionality without compromising system
responsiveness.

\subsubsection{Display and Keyboard}

The AGC featured a distinctive human-machine interface called the \textit{Display and
Keyboard} (\textbf{DSKY}), which allowed astronauts to interact with the computer using
a structured \textit{verb-noun paradigm}. Commands were constructed by selecting a
\textit{verb} (action) followed by a \textit{noun} (object), mirroring natural
language. For example, the command ``Verb 06 Noun 36'' instructed the AGC to display
the current time.

This consistent, intuitive interface enabled astronauts to monitor spacecraft systems,
execute computations, and perform maneuvering operations precisely and reliably.
