\section{Error Handling and Recovery}
\label{sec:rec}

Linux invests significant resources into isolating, detecting, and recovering from
runtime errors, whether caused by external events or internal bugs. However, on
resource-constrained hardware like the Cortex-M0 or the AGC, such extensive error
handling is nearly impossible due to hardware limitations. Instead, the AGC developers
adopted a radically simpler approach: perform a clean system restart after any detected
error.

Of course, an unexpected restart during a critical operation could leave the system in
an undefined state. To address this, the AGC introduced a mechanism allowing processes
to register recovery routines. Similarly, Apollo-RTOS adopts this strategy: critical
processes can register recovery table entries so that, if an error triggers a restart,
the system can recover to a safe state.

Despite its simplicity, this strategy proves highly effective on small systems, as
demonstrated by the success of the Apollo missions themselves.

\subsection{Error Handling}

Since the Cortex-M0 lacks a memory protection unit (MPU) for RAM, it is practically
impossible to detect memory corruption caused by unauthorized writes at the hardware
level—just as it was in the AGC. Consequently, error detection must be implemented
entirely in software.

Apollo-RTOS follows a similar philosophy to the AGC. Error detection is performed
through extensive software checks: function arguments and critical memory locations are
validated using assertions. This is carried out via calls to
\lstinline[style=myagc]|assert|, which first verifies the condition and, upon failure,
triggers a recovery procedure based on the severity: 
\begin{itemize}
    \item \lstinline[style=myagc]|H_RESET|: A hardware reset of the device is required.
    \item \lstinline[style=myagc]|S_RESET|: A system-wide software reset is sufficient.
    \item \lstinline[style=myagc]|TERM|: Only the faulty process must be terminated.
\end{itemize}

\begin{lstlisting}[
    style=myagc,
    caption={\file{include/utility/debug.h}},
    linebackgroundcolor={\line{5}\line{26} \lines{10}{11} \lines{16}{17} \lines{21}{22}},
    emph={[6]reset_lev_t},
    emphstyle={[6]\typestyle},
    emph={[7]__assert, trigger_hardfault, trigger_reset, trigger_term, HARDFAULT_MAGIC,
    __FILENAME__, __LINE__},
    emphstyle={[7]\stdlibstyle},
]
template <reset_lev_t lev, typename... Args>
void __assert(bool ex, const char *file, uint32_t line, Args &&...args)
{
  if (ex)
    return; // condition verified, nothing else to do

  if constexpr (lev == H_RESET) {
    /* if any debug statement is supplied in args, print it */
    /* copy file name and line number to registers r0, r1 */
    return trigger_hardfault(); 
        // print debug information and wait for manual intervention
  }

  if constexpr (lev == S_RESET) {
    /* print debug statement */
    return trigger_reset();
        // cause the system to restart automatically
  }

  if constexpr (lev == TERM) {
    return trigger_term();
        // terminate and cleanup the faulty process and carry on normally
  }
}

#define assert(EX, LEV, ...) __assert<LEV>((EX), __FILENAME__, __LINE__)
\end{lstlisting}

Once a hardfault interrupt is raised, hardware pushes some registers onto the stack as
described in \autoref{hard_context}. In the \lstinline[style=myagc]|hardfault_handler|
we first manually push the software saved registers \autoref{soft_context} onto the
stack, completing the context frame. The handler then prints available debug
information, offering two recovery options:
\begin{itemize}
    \item Manual intervention by pressing \texttt{<CTRL+D>} to trigger a software
        reset.
    \item Performing a hardware reset by manually pressing the reset button on the
        board.
\end{itemize}

\begin{lstlisting}[
    style=myagc,
    caption={\file{src/core/hardfault.cpp}},
    emph={[6]context_t, __extern_C__},
    emphstyle={[6]\typestyle},
    emph={[7]__assert, trigger_hardfault, trigger_reset, trigger_term, CTRL,
    hardfault_handler_body},
    emphstyle={[7]\stdlibstyle},
]
__extern_C__ void hardfault_handler_body(context_t *fault_stack)
{
  // disable all interrupts

  if (/* hardfault was triggered by an assert statement */) {
    /* print the source file name and line number */
  }

  /* print the register values at the point of the hardfault */

  while (1) {
    switch (serial::getc()) {
    case CTRL('d'):
      trigger_reset();
      break;

    case '?':
      /* print a trace of the system resources */
      break;
    }
  }
}
\end{lstlisting}


\subsection{Recovery Table}
\label{sec:rec_tbl}

When a process or a function enters a critical section, it can be unexpectedly
terminated by three main causes:
\begin{itemize}
    \item A hardware reset caused by pressing the power button,
    \item An unexpected loss of power, or
    \item A software-triggered reset following error detection.
\end{itemize}
We assume that a hardware reset is a deliberate action to restart everything from
scratch. This leaves the other two scenarios, which critical sections must be protected
against.

On the frontend, two RAII classes allow a process or function to set up recovery table
entries:
\begin{itemize}
    \item \lstinline[style=myagc]|guard_proc|: Used by a process to declare, ``I am
        entering a critical section; if a reset occurs, restart me with this recovery
        data.'' Upon recovery, the process can decide how to proceed based on the stored
        data.
    \item \lstinline[style=myagc]|guard_task|: Used by a process or function to register
        a task that must be executed at the next startup if a reset occurs mid-critical
        section. This is useful for cleanup or initiating new processes.
\end{itemize}

Recovery entries can be associated with two levels:
\begin{itemize}
    \item \lstinline[style=myagc]|RESET|: Recover from both a software reset and a power
        failure.
    \item \lstinline[style=myagc]|POWER_OFF|: Recover only from a power failure.
\end{itemize}

\begin{lstlisting}[
    style=myagc,
    caption={\file{include/core/recover.h}},
    emph={[6]rec_id_t},
    emphstyle={[6]\typestyle},
    linebackgroundcolor={\line{4} \lines{12}{13}},
]
struct guard_proc {
  // setup a recovery table entry at the start of the critical section
  //   to restart the current process 
  guard_proc(lev_t lev, const uint8_t *data, size_t data_sz);

  // remove the entry when exiting from the critical section
  ~guard_proc();
};

struct guard_task {
  // setup a recovery task to be run at startup 
  guard_task(lev_t lev, runnable_t task, time_t interval,
             const uint8_t *data, size_t data_sz);

  ~guard_task();
};
\end{lstlisting}

Internally, the recovery mechanism is backed by two tables:
\begin{itemize}[left=0pt]
    \item \lstinline[style=myagc]|proc_tbl|: Contains entries for recovering processes.
        Each entry includes:
\begin{lstlisting}[
    style=myagc,
    emph={[6]proc_entry_t, task_entry_t},
    emphstyle={[6]\typestyle},
]
struct proc_entry_t {
  uint32_t lev; // recovery level
  const proc_def_t *proc_def; // definition of the process to recover

  uint8_t data[N_REC_DATA] = {0xFF};
  uint16_t data_sz;
};
\end{lstlisting}

    \item \lstinline[style=myagc]|task_tbl|: Contains entries for recovering tasks.
\begin{lstlisting}[
    style=myagc,
    emph={[6]proc_entry_t, task_entry_t},
    emphstyle={[6]\typestyle},
]
struct task_entry_t {
  uint32_t lev; // Recovery level
  runnable_t task = nullptr; // task to run at recovery
  time_t interval = 0;

  uint8_t data[N_REC_DATA] = {0xFF};
  uint16_t data_sz;
};
\end{lstlisting}
\end{itemize}

The recovery tables are stored in a file on the FRAM file system, ensuring persistence
even across power failures. When an entry is updated, only that specific entry is
synchronized with the file system, minimizing the cost of each transaction.

\textbf{Recovery}: Upon detection of an error that issues a system reset, or after a
power outage, the startup code distinguishes whether it is recovering from a software
reset or a power failure. It then carries out the recovery procedures according to the
recovery table entries.

\begin{lstlisting}[
    style=myagc,
    caption={\file{src/core/recover.cpp}},
    emph={[6]proc_entry_t, task_entry_t},
    emphstyle={[6]\typestyle},
    emph={[7]recover, enabled, task, recover_proc, recover_task, copy_data},
    emphstyle={[7]\stdlibstyle},
    linebackgroundcolor={\line{12} \lines{16}{18} \line{24} \line{1} \line{26}},
    label={code:recover}
]
void recover(lev_t curr_lev) // recovery level: RESET or POWER_OFF
{
  for (auto &entry : task_tbl)  // first run the recovery tasks
    recover_task(entry, curr_lev);
  for (auto &entry : proc_tbl)  // then recover the processes
    recover_proc(entry, curr_lev);
  /* reset the tables */
}

void recover_task(auto &entry, lev_t curr_lev)
{
  if (!entry.enabled(curr_lev)) // if entry is not enabled for this level
    return;

  auto ptr = entry.copy_data();
  (interval == 0) 
    ? entry.task(ptr) // immediately run the task
    : waitlist::reg("recover", entry.interval, entry.task, ptr);
        // or set up a waitlist task to be run later
}

void recover_proc(auto &entry, lev_t curr_lev)
{
  if (!entry.enabled(curr_lev))
    return;
  sched::reg_proc(entry.proc_def, entry.copy_data()); // schedule the process
}
\end{lstlisting}
