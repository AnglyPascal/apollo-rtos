\section{Drivers}
\label{sec:drivers}

Drivers provide abstractions for interacting with hardware components, shielding
applications from low-level register operations.

\subsection{Timers}

The Nordic nRF51 on the \texttt{micro:bit} includes one 32-bit timer
(\lstinline[style=myagc]|TIMER0|) and two 16-bit timers
(\lstinline[style=myagc]|TIMER1|, \lstinline[style=myagc]|TIMER2|) \citep{board_trm}.
Apollo-RTOS configures the 16-bit timers as 1MHz timers, generating interrupts every
1ms, inspired by \citet{microbian}. 
\begin{itemize}
    \item \lstinline[style=myagc]|TIMER1| — Maintains the system clock and triggers
        waitlist tasks (\autoref{sec:waitlist}).
    \item \lstinline[style=myagc]|TIMER2| — Used experimentally for profiling.
\end{itemize}

\lstinline[style=myagc]|TIMER1|'s interrupt handler checks the waitlist periodically.
Since the interrupt can occur anywhere, waitlist tasks are run on a separate stack to
prevent corruption:

\begin{lstlisting}[
    style=myagc,
    caption={\file{src/drivers/timer.cpp}},
    emph={[6]timer1_handler},
    emphstyle={[6]\stdlibstyle},
    linebackgroundcolor={\line{4} \line{13} \line{15} \line{18}},
]
__extern_C__ void timer1_handler(void)
{
  if (TIMER1.COMPARE[0]) {
    MILLIS += 1; // increment system time
    TIMER1.COMPARE[0] = 0;
  }

  if (/* task with expired deadline exsits */) {
    intr_guard guard;

    // setup temporary stk to run waitlist tasks
    auto prev_stk = (uint8_t *)get_msp();
    set_msp(stk_end); 

    waitlist::run();

    // restore the original stack
    set_msp(prev_stk);
  }
}
\end{lstlisting}


\paragraph*{Profiling} Apollo-RTOS uses \lstinline[style=myagc]|TIMER2|, set up
independently of the system timer, to measure CPU time spent in each process.

Every 1ms, when \lstinline[style=myagc]|TIMER2| raises an interrupt, the
\lstinline[style=myagc]|timer2_handler| increments a counter associated with the
currently running process. A shell command \lstinline[style=mybash]|prof| displays the
runtime distribution:
\begin{lstlisting}[style=mytty]
>> prof
procs:
  |  shell: (0.864%)
  |  display: (55.567%)
  |  accel_bg: (0.34%)
  |  pkill: (0.165%)
  |  prof: (1.308%)
  |  htop: (14.349%)
  |  idle: (27.709%)
\end{lstlisting}

One limitation is that interrupts are disabled during scheduler operations like process
registration, priority changes, and context switching, making it difficult to precisely
measure the CPU time consumed by processes.

\subsection{Serial}

The serial driver manages the UART connection and provides three main functions:
\begin{itemize}
    \item \lstinline[style=myagc]|void busy_putc(char)|: transmits a character
        synchronously, busy-waiting until the transmission completes.
    \item \lstinline[style=myagc]|void intr_putc(char)|: transmits a character
        asynchronously. If a previous transmission is ongoing, the character is queued
        in a buffer. The \lstinline[style=myagc]|uart_handler|, triggered by a
        \lstinline[style=myagc]|TXDRDY| interrupt, sends queued characters. This design
        is inspired by \citet{microbian}.
    \item \lstinline[style=myagc]|char getc()|: waits for and receives a character
        synchronously.
\end{itemize}

\lstinline[style=myagc]|busy_putc| is used internally by
\lstinline[style=myagc]|kprintf| to print debug information atomically, while user
processes should use \lstinline[style=myagc]|printf|, which prints asynchronously via
\lstinline[style=myagc]|intr_putc|.

\paragraph*{Aside} Apollo-RTOS allows redirecting process outputs to files via the file
system’s streaming mechanism. For example:
\begin{lstlisting}[style=mytty]
>> echo this is a string sent to file 10 > 10
>> cat 10
this is a string sent to file 10
\end{lstlisting}
Internally, the serial output is treated as a special file named
\lstinline[style=myagc]|stdout|. Each process maintains an output file name, which
defaults to \lstinline[style=myagc]|stdout|, unless specified by an output filename in
shell the command: \lstinline[style=mytty]|> fn|.

This is achieved by an unified \lstinline[style=myagc]|printf| implementation, that
prints to the output file of the process, be it \lstinline[style=myagc]|stdout|, or a
normal file.
\begin{lstlisting}[
    style=myagc,
    caption={\file{include/fs/iostream.h}},
    linebackgroundcolor={\line{9}},
    mathescape=true,
]
template <typename... Args>
void fprintf(fn_t fn, Args... args);
// if fn == stdout, print to the serial bus using serial::intr_putc
// otherwise print to the file using $\text{\autoref{code:ostream}}$

template <typename... Args>
void printf(Args... args)
{
  fprintf(/* output file name of curr_proc */, std::forward<Args>(args)...);
}
\end{lstlisting}


\subsubsection*{Receiving Inputs from UART}

Apollo-RTOS uses a stack of listeners %
(\lstinline[style=myagc]|bool (*listener_t)(char)|) to allow processes to
asynchronously receive UART characters. A process that wishes to receive input pushes a
listener onto the top of this stack. 

When a UART character is received, it is passed down the listener stack until a
listener consumes it, at which point propagation stops. The bottom-most listener is
registered by the \lstinline[style=myagc]|shell| process, so by default all incoming
characters are handled by the shell.

\begin{lstlisting}[
    style=myagc,
    caption={\file{src/drivers/serial.cpp}},
    emph={[6]stack, listeners, uart_handler, register_listener, unregister_listener},
    emphstyle={[6]\stdlibstyle},
    mathescape=true,
]
using listener_t = bool (*)(char);
stack<listener_t, 16> listeners; // $\text{\autoref{ds:stack}}$

void register_listener(listener_t listener) { listeners.push(listener); }
void unregister_listener() { listeners.pop(); }

extern "C" void uart_handler(void)
{
  if (UART.RXDRDY) {
    char c = UART.RXD;

    // send the character down the stack
    for (auto listener: listeners)
      if (listener(c))
        break;

    UART.RXDRDY = 0;
  }

  // ... the rest
}
\end{lstlisting}


\subsection{I2C}

The I2C master on the Nordic nRF51 enables communication with devices connected to the
\texttt{micro:bit} via the I2C bus. It operates at 100KHz or 400KHz; Apollo-RTOS uses
the 100KHz setting following \citet{microbian}.

Apollo-RTOS provides two I2C driver modes:
\begin{itemize}
    \item \textbf{Synchronous mode:} Busy-waits for each read/write operation. Used
        before the scheduler starts. Also used by the recovery module to atomically
        write table entries to the FRAM.
    \item \textbf{Asynchronous mode:} Once the scheduler is active, a mutex
        synchronizes I2C operations across processes. While multiple interrupts occur
        during transmission, the process sleeps during communication, maintaining the
        illusion of atomicity.
\end{itemize}

The I2C communication process is as follows:
\begin{itemize}[left=0pt]
    \item The slave device address (\lstinline[style=myagc]|0x03–0x77|) is written to
    \lstinline[style=myagc]|I2C0.ADDRESS|.
    \item Command bytes are sent sequentially, each acknowledged by an interrupt.
    \item After command transmission:
        \begin{itemize}
            \item For writes: Data bytes are sent with acknowledgments.
            \item For reads: 
                \begin{itemize}
                    \item \lstinline[style=myagc]|STARTRX| is set.
                    \item If reading the last byte, \lstinline[style=myagc]|STOP| is
                        set; otherwise, \lstinline[style=myagc]|SUSPEND| is set.
                    \item Data is read from \lstinline[style=myagc]|RXD| after an
                        interrupt.
                    \item If more bytes are needed, \lstinline[style=myagc]|RESUME| is
                        triggered.
                \end{itemize}
        \end{itemize}
\end{itemize}

The synchronous I2C communication is simple: read/write each byte following the
communication protocol, and busy-wait until it finishes. The asynchronous communication
is more interested, and is managed by a simple state machine with four states:
\begin{itemize}
    \item \lstinline[style=myagc]|W_CMD|: Writing command bytes.
    \item \lstinline[style=myagc]|TX_DATA|: Transmitting data.
    \item \lstinline[style=myagc]|RX_DATA|: Receiving data.
    \item \lstinline[style=myagc]|NACK|: Cleanup and finalization.
\end{itemize}
Once the transfer is started by the \lstinline[style=myagc]|xfer| function, the calling
process goes to sleep on a channel, and is woken up by the end of transfer.
\begin{lstlisting}[
    style=myagc,
    caption={\file{src/drivers/i2c\_async.h}}
]
template <bool READ>
int xfer(uint8_t addr,
         uint8_t *cmd, size_t cmd_sz, 
         uint8_t *buf, size_t buf_sz);
\end{lstlisting}

\lstinline[style=myagc]|xfer| first acquires an internal mutex. It then sets up the
transaction, disables \lstinline[style=myagc]|I2C_IRQ| to write initial registers, and
then re-enables the interrupt before sleeping on an internal channel until the
operation completes. The state machine logic is implemented in the interrupt handler
(\autoref{sec:i2c_async}).


\subsection{Display}
\label{proc:display}

The \(5 \times 5\) LED matrix on the \texttt{micro:bit} is arranged into three rows in
a somewhat complex format. To manage it, Apollo-RTOS uses convenience macros provided
by \citet{microbian}. The LEDs are controlled via GPIO registers and require constant
refreshing to maintain smooth animations.

The \lstinline[style=myagc]|display| driver is implemented as a low-priority service
process, always started during system initialization (\autoref{sched:init}). It
periodically renders the image stored in the global variable
\lstinline[style=myagc]|image|.

Processes can update the display by calling
\lstinline[style=myagc]|set_image(image_t)|, which modifies the global
\lstinline[style=myagc]|image| variable with the new desired display frame.
