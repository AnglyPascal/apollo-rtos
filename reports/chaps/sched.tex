\section{Scheduling: Co-operative and Pre-emptive}

The core scheduler of Apollo-RTOS is a priority-based cooperative scheduler. It allows
the highest-priority process to run indefinitely until it voluntarily gives up
execution, at which point other processes are given the opportunity to run. This simple
approach offers several benefits:

\begin{itemize}
    \item Simplicity: The implementation is straightforward.
    \item Fewer race conditions: Since one process never preempts another, data races
        on shared variables are largely eliminated.
\end{itemize}

However, processes must be aware of their runtime context and yield execution
periodically to prevent deadlocks. This can be done in two ways:
\begin{itemize}
    \item Lowering their priority.
    \item Going to sleep.
\end{itemize}

With this design, the interface for process creation and management remains simple:

\begin{lstlisting}[style=myagc,]
// Register a process defined by 'proc_def', passing 'param' as an argument
pid_t reg_proc(const proc_def_t *proc_def, void *param);

// Increase the priority
void incr_priority(pid_t pid, priority_t priority);

// Decrease the priority
void decr_priority(priority_t priority);
\end{lstlisting}

Defining a process is minimalistic:

\begin{lstlisting}[style=myagc,]
struct proc_def_t {
  string      name;
  priority_t  priority;
  size_t      stk_sz;
  runnable_t  func;       // where runnable_t = void ()(void);
};
\end{lstlisting}

At runtime, each process is represented in a process descriptor table, which stores essential metadata about active processes. The most important fields are:

\begin{lstlisting}[style=myagc]
struct proc_t {
  priority_t  priority;   // Current priority
  byte_t      *stk_ptr;   // Current stack pointer
  byte_t      *stack;     // Start of the stack area
  size_t      stk_sz;     // Stack size
  void        *param;     // Parameter passed to the process function
  // ... other fields
};
\end{lstlisting}

Stack Layout in Arm Cortex-M0

To understand the scheduling mechanism, we first examine the stack layout in the Arm Cortex-M0 architecture:

\begin{emptythm}
    The stack in Arm architecture starts at a higher address and grows downward.

    When execution is preempted by an interrupt, the hardware automatically pushes key
    registers onto the stack in the following order (from lower to higher addresses):
\begin{lstlisting}[style=mytxt]
       new stack pointer -> |                               
                            |  r0                          
                            |  r1                          
                    ^       |  r2                          
       stack grows  |       |  r3                          
       downwards    |       |  r12                         
                            |  lr      Link register       
                            |  pc      Program counter     
       old stack pointer -> |  psr     Status register     
\end{lstlisting}
To enable context switching between processes, additional registers must be saved
manually. This is done via software, giving us control over the order. We chose the
following layout:
\begin{lstlisting}[style=mytxt]
       new stack pointer -> |                               
                            |  r8
                            |  r9
                            |  r10
                            |  r11
                            |  r4
                            |  r5
                            |  r6
    stack pointer after     |  r7
    hardware pushes regs -> |  lr_intr   Return from interrupt address
\end{lstlisting}

\end{emptythm}

With the stack management details covered, we can now discuss how the scheduling
algorithm works.

\subsection{Process Creation}

The implementation of \lstinline[style=myagc]|reg_proc| can be summarized as follows:

\begin{lstlisting}[
    style=myagc,
    linebackgroundcolor={ \line{4} \line{7} \line{8} },
    title={\file{src/core/sched.cpp}}
]
pid_t reg_proc(const proc_def_t *def, void *param)
{
  auto [name, priority, stk_sz, proc_func] = *def;
  proc_t *proc = procs.alloc();  // allocate a process descriptor
  proc->param = param;  // store the param for future cleanup

  stack_allocator.acquire(proc, stk_sz, proc_func, param, exit);
  incr_priority(pid, priority);

  // ...
  return pid;
}
\end{lstlisting}

The key operations occur on lines 7 and 8. In line 7, the local pool allocator assigns
a block of memory of size \lstinline[style=myagc]|stk_sz| and initializes it with the
required parameters.

\begin{emptythm}
    A newly created process is treated as if it has just undergone a context switch.
    This means the stack must be set up with the appropriate register values in the
    correct order, as discussed earlier. Line 7 ensures this setup is performed
    correctly.
\end{emptythm}

Examining the \lstinline[style=myagc]|acquire| function:

\begin{lstlisting}[
    style=myagc,
    linebackgroundcolor={\lines{10}{14}},
    title={\file{src/core/stack\_allocator.h}}
]
void acquire(proc_t *proc, size_t stk_sz, runnable_t func, void *param,
             void (*ret)())
{
  proc->stack = (byte_t *)pool.alloc(stk_sz);  // allocate the stack
  // ...

  auto stk_ptr = (context_t *)(proc->stack + stk_sz - sizeof(context_t));

  // setup initial stack frame
  stk_ptr->psr     = init_psr;        // 0x01000000 to enable Thumb mode
  stk_ptr->pc      = (uint32_t)func;  // entry to the process
  stk_ptr->lr      = (uint32_t)ret;   // exit from the process
  stk_ptr->r0      = (uint32_t)param; // parameter
  stk_ptr->lr_intr = lr_intr_magic;   // return address from interrupts

  proc->stk_ptr = (byte_t *)stk_ptr;
  proc->stk_sz = stk_sz;
}
\end{lstlisting}

Lines 10-14 populate the process context. The entry point is stored in the \texttt{pc} register, the exit sequence in the \texttt{lr} register, and the process parameter in \texttt{r0}. The interrupt return address is also set.

\subsection{Priority Modification}

A singleton object, \lstinline[style=myagc]|cpu|, tracks the currently running process and the highest-priority process:

\begin{lstlisting}[style=myagc, title={\file{src/core/sched.cpp}}]
volatile struct {
  proc_t *hi_proc = nullptr;    // highest priority process
  proc_t *curr_proc = nullptr;  // currently running process
} cpu;
\end{lstlisting}
This object functions similarly to the \texttt{NEWJOB} register in the AGC. When a process is created, its priority is compared with the highest-priority process. If it is higher, \lstinline[style=myagc]|hi_proc| is updated.

In \lstinline[style=myagc]|reg_proc| (line 8), \lstinline[style=myagc]|incr_priority| is called:

\begin{lstlisting}[
    style=myagc,
    title={\file{src/core/sched.cpp}},
    linebackgroundcolor={\lines{6}{7}},
]
void incr_priority(pid_t pid, priority_t priority)
{
  proc_t *proc = procs[pid];
  // ... disable interrupts
  proc->priority = priority; // set priority
  if (cpu.hi_proc == nullptr || cpu.hi_proc->priority < priority)
    cpu.hi_proc = proc;
}
\end{lstlisting}

When a high-priority process completes its critical section, it should lower its priority to allow other processes to run:

\begin{lstlisting}[
    style=myagc,
    title={\file{src/core/sched.cpp}},
    linebackgroundcolor={\lines{4}{5}},
]
void decr_priority(priority_t priority)
{
  cpu.curr_proc->priority = priority;
  cpu.hi_proc = procs.max_priority();
  change_proc();
}
\end{lstlisting}

The highest-priority process is updated, and \lstinline[style=myagc]|change_proc| is called to check if a context switch is needed:

\begin{lstlisting}[
    style=myagc,
    title={\file{src/core/sched.cpp}},
    linebackgroundcolor={\lines{4}{5}},
]
void change_proc()
{
  // enable interrupts
  if (cpu.hi_proc != cpu.curr_proc)
    reschedule();   // triggers pendsv interrupt
}
\end{lstlisting}

Now, we examine how context switching is performed.

\subsection{Context Switching}

When \lstinline[style=myagc]|reschedule()| triggers the \lstinline[style=myagc]|pendsv| interrupt, the hardware first pushes key registers onto the stack. Then, \lstinline[style=myagc]|pendsv_handler| is called. We then save additional registers, swap stack pointers, and restore the state for the new process.

The register saving/restoring is handled in assembly, while stack pointer swapping is done in C++:

\begin{lstlisting}[style=myarm, title={\file{src/mpx.s}}]
@@@ push software-saved registers onto stack
  .macro isave
  push {r4-r7, lr}            @ Copy from high to low
  mov r4, r8
  mov r5, r9
  mov r6, r10
  mov r7, r11
  push {r4-r7}
  mrs r0, msp                 @ Copy from high to low
  .endm

@@@ pop software-saved registers
  .macro irestore             @ Expect process sp in r0
  msr msp, r0
  pop {r4-r7}
  mov r11, r7
  mov r10, r6
  mov r9, r5
  mov r8, r4
  pop {r4-r7}
  pop {pc}                    @ pop lr into pc, jumping to new process
  .endm

@@@ PendSV handler for context switching
  .global pendsv_handler
  .thumb_func
pendsv_handler:
  isave                       @ Save current process state
  bl cxt_switch               @ Select new process
  irestore                    @ Restore new process state
\end{lstlisting}

The definition of \lstinline[style=myagc]|cxt_switch|:

\begin{lstlisting}[
    style=myagc,
    title={\file{src/core/sched.cpp}},
    linebackgroundcolor={\line{6} \lines{8}{9}},
]
void *cxt_switch(void stk_ptr)
{
  if (/* cpu.curr_proc is done */)
    /* release resources */
  else
    cpu.curr_proc->stk_ptr = (byte_t *)stk_ptr;  // store old stk_ptr

  cpu.curr_proc = cpu.hi_proc;
  return cpu.hi_proc->stk_ptr;  // restore new stk_ptr
}
\end{lstlisting}


\subsection{Process Suspension}

A process can voluntarily yield execution either by lowering its priority or by
suspending execution (sleeping) to be woken up later.

The wake-up mechanism is more involved, so we will discuss it in two parts. A process
can wake up in one of two ways:
\begin{itemize}
    \item By setting an alarm when going to sleep, which wakes it up after a specified
        time.
    \item By waiting for a specific event to occur before resuming execution.
\end{itemize}
The first method relies on the waitlist, while the second requires a synchronization
mechanism. We will first discuss process suspension before covering these mechanisms.

\begin{emptythm}
    A runnable process is represented by a positive priority value. To put a process to
    sleep while preserving its original priority, we simply negate its priority.
\end{emptythm}

\begin{lstlisting}[
    style=myagc,
    title={\file{src/core/sched.cpp}},
    linebackgroundcolor={\line{8}},
]
void sleep(time_t period = 0)
{
  if (period > 0)
   /* set an alarm in the waitlist */
  /* else suspend execution until another process wakes me up */

  // Negate priority to mark process as ASLEEP
  decr_priority(-cpu.curr_proc->priority);
}
\end{lstlisting}

A process that wants to wake up a sleeping process simply negates its priority:

\begin{lstlisting}[
    style=myagc,
    title={\file{src/core/sched.cpp}},
    linebackgroundcolor={\line{2}},
]
void wakeup(pid_t pid) {
  incr_priority(pid, -procs[pid]->priority);
}
\end{lstlisting}


\subsection{Waitlist: Preemptive Scheduling}

The waitlist is implemented as a sorted linked list of tasks:

\begin{lstlisting}[
  style=myagc,
  title={\file{src/core/waitlist.cpp}},
  linebackgroundcolor={\line{5}},
]
struct waitlist_t {
  time_t remaining = 0;
  runnable_t func = nullptr;
  void *param = nullptr;
  waitlist_t *next = nullptr;  // Linked list link
};
\end{lstlisting}

\begin{emptythm}
    If a task \(t_0\) is scheduled to run in \(n_0\) ticks, it is placed in the waitlist between tasks
    \(t_1\) and \(t_2\) such that if \(t_1\) and \(t_2\) have deadlines \(n_1\) and
    \(n_2\), then \(n_1 \le n_0 \le n_2\). We set:
    \[\texttt{remaining} = n_0 - n_1\]
    Thus, the time until executes is the sum of the \texttt{remaining} values for all
    preceding tasks.
\end{emptythm}

This algorithm, originally used in the AGC, has key implications:
\begin{itemize}
    \item Maintaining a sorted linked list has insertion complexity. However, with an
        upper limit of \lstinline[style=myagc]|N_WAITLIST = 16|, this cost is
        negligible.
    \item Using remaining values, we only need to check the first task on each timer
        tick, reducing computational overhead.
\end{itemize}

Task registration and execution are implemented as follows:

\begin{lstlisting}[
    style=myagc,
    title={\file{src/core/waitlist.cpp}},
    linebackgroundcolor={\line{3} \line{8} \line{16} \line{18}},
]
void reg(string name, time_t interval, runnable_t func, void *param)
{
  waitlist_t *task = alloc();
  waitlist_t *hd = &waitlist_hd;
  time_t prev = 0;
  while (hd->next != nullptr && prev + hd->next->remaining <= interval) {
    prev += hd->next->remaining;
    hd = hd->next;
  }
  time_t remaining = interval - prev;

  if (hd->next != nullptr)
    hd->next->remaining -= remaining;

  *task = {name, remaining, func, param, hd->next};
  hd->next = task;
}
\end{lstlisting}

During a timer interrupt, expired tasks are executed:

\begin{lstlisting}[
    style=myagc,
    title={\file{src/core/waitlist.cpp}},
    linebackgroundcolor={\line{5} \line{13}},
]
void run()
{
  auto head = &waitlist_hd;
  if (head->next != nullptr)
    head->next->remaining -= update_interval;

  while (head->next != nullptr && head->next->remaining == 0) {
    auto task = head->next;
    head->next = task->next;

    auto [name, remaining, func, param, next] = *task;
    dealloc(task);
    func(param);
  }
}
\end{lstlisting}

This approach minimizes overhead in interrupt-inhibited situations, making it ideal for
real-time constraints.

\subsubsection{Wakeup Alarm}

With the waitlist implemented, setting up an alarm is simple:

\begin{lstlisting}[
    style=myagc,
    title={\file{src/core/sched.cpp}},
    linebackgroundcolor={\lines{5}{8} \line{11}},
]
void sleep(time_t period = 0)
{
  auto proc = cpu.curr_proc;

  auto default_alarm = [](void *ptr) {
    auto proc = (proc_t )ptr;
    incr_priority(/ pid of proc */, -proc->priority);
  };

  if (period > 0)
    waitlist::reg(proc->name, period, default_alarm, (void *)proc);

  decr_priority(-proc->priority);
}
\end{lstlisting}

\subsection{Synchronization Mechanism}

We implement channels for synchronization, using a FIFO queue of waiting processes
based on \texttt{circular\_buffer}:

\begin{lstlisting}[
    style=myagc,
    title=\file{include/core/sched.h},
]
template <size_t chan_len>
struct chan_t : public circular_buffer<pid_t, chan_len> {};
\end{lstlisting}

A process waiting for an event enqueues itself and sleeps, while another process
signals the event by dequeuing and waking it up:

\begin{lstlisting}[
    style=myagc,
    title=\file{include/core/sched.h},
    linebackgroundcolor={\line{5} \line{15} \line{23}}
]
template <size_t chan_len>
void wait(chan_t<chan_len> &chan)
{
  intr_guard guard;
  chan.enqueue(/* current process */);
  sleep();
}

template <size_t chan_len>
void notify(chan_t<chan_len> &chan)
{
  intr_guard guard;
  if (chan.empty())
    return;
  wakeup(chan.dequeue());
}

template <size_t chan_len>
void notify_all(chan_t<chan_len> &chan)
{
  intr_guard guard;
  while (!chan.empty())
    wakeup(chan.dequeue());
}
\end{lstlisting}

Using channels and \lstinline[style=myagc]|wait, notify|, we can implement a
\lstinline[style=myagc]|mutex| 

\begin{lstlisting}[
    style=myagc,
    title={\file{include/utility/mutex.h}},
    linebackgroundcolor={\line{10} \line{17} \line{23}}
]
template <size_t chan_len>
class mutex {
  chan_t<chan_len> lock_chan;
  bool busy = false;

public:
  void lock()
  {
    while (busy)
      sched::wait(lock_chan);
    busy = true;
  }

  void unlock()
  {
    busy = false;
    sched::notify(lock_chan);
  }
};
\end{lstlisting}

Usually we acquare a mutex before a critical section, and then release it at the end of
the section. Using the RAII paradigm, we can implement a class
\lstinline[style=myagc]|lock_guard| (named after
\lstinline[style=myagc]|std::lock_guard|) that acquire the mutex upon construction, and
releases it in its destructor, giving a simple interface for locking.

\begin{lstlisting}[
    style=myagc,
    title={\file{include/utility/mutex.h}},
    linebackgroundcolor={\lines{6}{7}}
]
template <typename _mutex>
class lock_guard {
  _mutex &_m;

public:
  lock_guard(_mutex &_m) : _m{_m} { _m.lock(); }
  ~lock_guard() { _m.unlock(); }
};
\end{lstlisting}

\subsubsection{Interrupts management}

We also implement a similar mechanism for disabling and enabling interrupts before and
after a cricital section. This implementation uses template type deduction to choose
between the two scenarios when we want to disable all interrupts vs disable only one
interrupt:

\begin{lstlisting}[
    style=myagc,
    title={\file{include/core/irq.h}},
    linebackgroundcolor={\lines{7}{18}, \lines{21}{34}}
]
template <typename T>
class intr_guard
{
  int irq;

public:
  // when no argument is passed, deduce T = void & disable all interrupts
  intr_guard(void) requires std::same_as<T, void>
    : irq{get_primask()}                                                
  {                                                     +-------------+
    intr_disable();                                     |  T == void  |
  }                                                     |  all irqs   |
                                                        +-------------+
  // re-enable all interrupts if T = void
  ~intr_guard() requires std::same_as<T, void>
  { 
    set_primask(irq); 
  }


  // if an arugment is passed, deduce T = int, and disable only that irq
  intr_guard(int irq) requires std::same_as<T, int>
    : irq{irq}
  {                                                     +-------------+
    disable_irq(irq);                                   |  T == int   |
  }                                                     |  one irq    |
                                                        +-------------+

  // if T = int, enable only that irq
  ~intr_guard() requires std::same_as<T, int>
  {
    clear_pending(irq);
    enable_irq(irq);
  }
};

// type deduction hints for the constructor
intr_guard(void) -> intr_guard<void>;
intr_guard(int) -> intr_guard<int>;
\end{lstlisting}

This interface is then used simply as:
\begin{lstlisting}[style=myagc]
{ // critical section
  intr_guard guard; // disable all interrupts and re-enable at the end
}

{ // critical section
  intr_guard guard{UART_IRQ}; // disable only the UART interrupt
}
\end{lstlisting}
