\section{Memory Management and File System}
\label{sec:memory}

\subsection{Dynamic Memory Allocation}
\label{sec:mem}

A central component of Apollo-RTOS is its memory management system, which employs pool
allocators for all runtime allocations. This design provides simple, efficient, and
predictable dynamic memory management.

\begin{emptythm}
    \begin{itemize}[left=1em]
        \item The allocator maintains a linked list of free memory chunks.
        \item It searches the free list for a sufficiently large chunk during
            allocation.
        \item If no suitable chunk is found, it requests additional memory from the
            global allocator.
        \item Freed chunks are returned to the free list for reuse.
    \end{itemize}
\end{emptythm}

The allocator implementation (\autoref{ds:allocator}) is based on a doubly linked
freelist (\autoref{ds:list}) with statically allocated nodes, avoiding dynamic memory
allocations for list operations. It exposes a simple interface:

\begin{lstlisting}[style=myagc]
template <allocator_t alloc_func, size_t alignment>
class allocator {
public:
    byte_t *alloc(size_t sz);
    void dealloc(byte_t *ptr);
};
\end{lstlisting}

Apollo-RTOS provides two separate sets of memory allocation interfaces:
\begin{itemize}
    \item \lstinline[style=myagc]|kmalloc| and \lstinline[style=myagc]|kfree| for
        kernel-space allocations.
    \item \lstinline[style=myagc]|malloc| and \lstinline[style=myagc]|free| for
        process-space allocations.
\end{itemize}

Each process descriptor maintains a linked list of all memory blocks allocated through
\lstinline[style=myagc]|malloc|. This design serves two critical purposes:
\begin{itemize}
    \item It ensures proper memory cleanup at process termination—automatically
        reclaiming any blocks not explicitly freed.
    \item It provides basic memory accounting and isolation between processes, despite
        the absence of hardware memory protection on the Cortex-M0.
\end{itemize}

The combination of kernel and process-specific allocators, along with explicit tracking
of allocations per process, creates a robust memory management system that prevents
memory leaks and maintains strict separation between memory domains. More details on
the actual implementation can be found at \autoref{impl:malloc}.


\subsection{File System}
\label{sec:fs}

Apollo-RTOS implements a dual-storage architecture that leverages both the
\texttt{micro:bit}'s onboard flash and an external FRAM chip, each serving distinct
roles based on their respective characteristics. This design carefully balances
performance, endurance, and access patterns to provide an efficient and reliable
storage solution.

\paragraph*{Flash Memory} The 256KB onboard flash serves as the primary storage medium,
with approximately 90KB occupied by the Apollo-RTOS binary. Flash memory offers direct
CPU access for fast read operations but imposes significant write constraints. Writes
require erasing entire 1KB pages (22.3 ms) before programming (20 $\mu$s per byte)
\citep{board_spec}, making small, frequent updates inefficient. Its endurance of
approximately 20,000 erase cycles and 10-year data retention makes it ideal for storing
relatively static data that is read often but modified infrequently, such as operating
system binaries and configuration files.

\paragraph*{FRAM Storage} The MB85RC2567 FRAM chip \citep{fram} complements flash
memory by offering superior endurance and write performance. Supporting up to
\(10^{12}\) write cycles and 95+ years of data retention, the 32KB FRAM is ideal for
frequently updated data. Although accessed over I2C at 100KHz—resulting in lower read
throughput compared to flash—it provides near-instantaneous write operations without
the need for erase cycles. Being an external device, FRAM introduces I2C bus overhead
and contention, which must be managed carefully at the system level.

\paragraph*{Unified File System Design} Rather than maintaining separate file systems,
Apollo-RTOS introduces an abstract block device layer that unifies access across
storage media. Each storage device is described by a \lstinline[style=myagc]|fs_desc_t|
structure (\autoref{fs:desc}) capturing device-specific parameters (e.g., block size,
capacity) and read/write operations. A template-based approach enables compile-time
optimization of storage access while maintaining a clean, extensible interface.

The file system is implemented entirely in headers under \texttt{include/fs/}, and uses
a two-level table structure with comprehensive metadata tracking. This design enables
efficient file management across heterogeneous storage devices, abstracting away
differences in performance and endurance at the application level.


\subsubsection{File System Backend}

The file system backend manages physical storage using two core data structures: an
inode table and a compact block allocation bitmap. The \lstinline[style=myagc]|inode_t|
structure represents each file's metadata and storage allocation, while the
\lstinline[style=myagc]|bitset| (\autoref{ds:bitset}) efficiently tracks free blocks
across the storage device.

Each file is physically represented as follows:

\begin{lstlisting}[
    style=myagc,
    caption={\file{include/fs/fs\_bck.h}},
    linebackgroundcolor={}
]
template <typename desc_t, desc_t desc>
struct inode_t {
  using addr_t = typename desc_t::addr_t;
  using blk_addr_t = uint8_t; 
    // in either flash or FRAM, blocks are addressed with 8-bit integers

  blk_addr_t blks[desc.max_num_blks]; // non-contiguous block ownership
  mutable addr_t end;   // logical end of file
  const uint8_t nblks;  // number of blocks assigned
  mutable uint8_t flag; // file status encoded as a byte
};
\end{lstlisting}

Files are referenced system-wide using their inode number, defined as \lstinline[style=myagc]|fn_t = uint8_t|.  
The backend exposes the following public interface:

\begin{lstlisting}[
    style=myagc,
    caption={\file{include/fs/fs\_bck.h}},
    linebackgroundcolor={}
]
template <...>
class fs_t
{
public:
  void format();
  void mount();    // loads header; formats if invalid
  void umount() const; // stores header back to device

  // Open a file using Linux-like flags (O_CREATE, O_WRITE, O_SHARED, etc.)
  pair<const inode_t *, bool> open(fn_t fn, size_t sz, uint32_t flags);

  void remove(fn_t fn, bool forced = false);

  // Load contents into a buffer
  template <bool sync = ASYNC>
  size_t load(const inode_t *inode, void *buf, size_t buf_sz, size_t off);

  // Store buffer contents into a file
  template <bool sync = ASYNC>
  size_t store(const inode_t *inode, const void *buf, size_t buf_sz, size_t off);
};
\end{lstlisting}

The detailed implementation of \lstinline[style=myagc]|open|, \lstinline[style=myagc]|load|, and \lstinline[style=myagc]|store| is presented in \autoref{fs:fs}.

\subsubsection{File System Frontend}

The file system frontend acts as the primary interface between user processes and physical storage. It wraps raw \lstinline[style=myagc]|inode_t| structures into manageable file objects and implements features such as access control, memory mapping, and streaming operations.

At its core lies the \textbf{file descriptor table}, maintaining state for all open files. Each descriptor (\lstinline[style=myagc]|fd_t|) tracks:
\begin{itemize}
    \item A reference to the underlying \lstinline[style=myagc]|inode_t|.
    \item Read/write access counters for concurrency management.
    \item Locking mechanisms for thread safety.
\end{itemize}

Descriptors are wrapped by \lstinline[style=myagc]|file_t| handlers, which:
\begin{itemize}
    \item Enforce access permissions.
    \item Synchronize concurrent accesses.
    \item Automatically release resources upon closure.
\end{itemize}

\paragraph*{Memory Mapping Subsystem} Apollo-RTOS supports runtime memory mapping of
file contents, enabling two modes:
\begin{itemize}
    \item \textbf{Private mapping}: Local to the process; modifications are isolated.
    \item \textbf{Shared mapping}: Accessible by multiple processes, enabling IPC-like
        behavior.
\end{itemize}

\paragraph*{Stream Abstraction Layer} Stream interfaces extend basic file operations to
enable buffered sequential access:
\begin{itemize}
    \item \lstinline[style=myagc]|ifstream| (\autoref{fs:ifstream}) reads characters
        sequentially, utilizing a read-ahead cache.
    \item \lstinline[style=myagc]|ofstream| (\autoref{fs:ofstream}) outputs formatted
        strings and individual characters efficiently.
\end{itemize}

\paragraph*{Unified I/O Model} Following Unix philosophy, Apollo-RTOS unifies file and
output streams. The function \lstinline[style=myagc]|do_printf| outputs formatted
strings to any stream:

\begin{lstlisting}[
    style=myagc,
    caption={\file{include/utility/format.h}},
    linebackgroundcolor={},
    label={code:ostream}
]
template <typename ostream>
  requires requires(ostream &os, char c) { { os.putc(c) }; }
__noinline__ void do_printf(ostream &os, const char *fmt, ...);
\end{lstlisting}

\paragraph*{File Handler Interface} The \lstinline[style=myagc]|file_t| class provides
a rich set of operations for file management:

\begin{lstlisting}[
    style=myagc,
    caption={\file{include/fs/fs\_impl.h}},
    linebackgroundcolor={}
]
class file_t {
  fd_t *fd = nullptr;
  /* memory mapping information */

public:
  file_t(fn_t fn, size_t sz, uint32_t flags);
  ~file_t();

  void *mmap(size_t sz);

  template <typename T, typename... Args>
    requires std::constructible_from<T, Args...>
  T *mmap(Args &&...args);

  template <typename T>
  void mmap(T &obj);

  void unmap();

  template <bool sync = ASYNC>
  bool load();

  template <bool sync = ASYNC>
  size_t store() const;

  template <bool sync = ASYNC>
  size_t write(const void *buf, size_t sz, size_t off = 0);

  template <bool sync = ASYNC>
  size_t append(const void *buf, size_t sz);

  template <bool sync = ASYNC>
  size_t read(uint8_t *buf, size_t len, size_t off = 0) const;
};
\end{lstlisting}

\subsubsection{File System Usage Example}

Finally, file system operations can be utilized as follows:

\begin{lstlisting}[
    style=myagc,
    caption={\file{apollo/test.cpp}},
    emph={[2] file_rw_test},
    emphstyle={[2]\stdlibstyle},
]
void file_rw_test()
{
  fn_t fn = 10;

  {
    auto file = fram::open(fn, 128, O_WRITE | O_CREATE);
    // create private mapping
    auto t = (char *)file.mmap(16); 

    const char *s = "It IS a string, ";
    while (*s != '\0')
      *t++ = *s++;
    *t = '\0';

    file.store(); 
    // file is closed automatically by destructor
  }

  {
    ofstream os{fn, O_CHAR_FILE};
    // string the formatted string to the file
    os.printf("and this is %c %s string", 'a', "formatted");
  } // file closed automatically

  {
    ifstream it{fn};
    while (*it != '\0') {
      fprintf(stdout, "%c", *it); // force output to stdout
      ++it;
    }
    fprintf(stdout, "\r\n");

    // should output: 
    // "It IS a string, and this is a formatted string"
  }
}
\end{lstlisting}
